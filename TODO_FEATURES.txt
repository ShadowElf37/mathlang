1. [PARTIAL] bytecode VM — lazy OnceLock compilation, stack-based interpreter, tensor
   indexing (Index), nested lambdas (MakeClosure), Def::Func in blocks, namespace
   members, forward references.

   1.0 [DONE v0.46.1] The Env is layered: a writable innermost frame over read-only
       layers, so entering a function costs one small allocation instead of cloning
       the globals and merging the closure's captured map into them (the old
       make_local). That merge was ~100% of the tree-walk call overhead — adding 300
       trivial globals made a fallback body 3.4x slower (2.1 s -> 7.1 s) while
       compiled code was untouched, and the cost/entry slope extrapolated to zero at
       ~126 entries against a base env of 135. Fallback bodies went 2.1 s -> 91 ms
       and no longer care how big the environment is. Consequence to preserve: a
       call frame layers [captured, globals] and deliberately NOT the caller's
       chain — splicing that in is both dynamic scoping and quadratic in recursion
       depth (it broke 90 000-deep recursion outright).

   Still possible to add to the bytecode VM:
   1.1 [DONE v0.46.2] EvalSub — the escape hatch that retired whole-body fallback.
       A node the compiler has no instruction for is interpreted *in place* rather
       than abandoning the body (and, because the OnceLock cached the failure,
       abandoning it permanently). Instruction::EvalSub{expr, binds} names the
       params/locals the node reads, resolved to slots at compile time, and the
       executor copies just those into a frame. Worth ~19-24% on a body that mixes
       supported and unsupported nodes (heavy arithmetic + one slice: 345 -> 278 ms).
       Roughly neutral when the body is dominated by unsupported nodes — Phase 1
       had already made falling back cheap, so this is structural more than fast:
       adding a real instruction is now a local optimization instead of a
       prerequisite for the body compiling at all.
       Guard to preserve: Splat and Named must never be EvalSub'd alone. They
       splice a *variable* number of slots into the enclosing list, so the
       enclosing call/tuple/array is interpreted whole. Missing this broke
       `[..u, x]`, `g(..cfg)` and `g(b=1, a=x)` inside bodies; tests.sh vm.splat.*
       and vm.named.* cover it.
       Also: compile_fn hands a body back (returns None) when it compiled to
       nothing but one whole-body EvalSub, since VM setup would buy nothing.

   1a. Slices in compiled bodies: T[lo..hi] is interpreted via EvalSub (~1.1 us
       per evaluation). A dedicated Slice instruction would remove that.
   1b. [MOOT] Ranges. `(lo..hi)` — the only range syntax there is, since a bare
       `1..5` does not parse outside index brackets — already works in a body via
       EvalSub. A dedicated instruction is the same optimization as 1a.
   1c. Tensor literals: (1,2; 3,4) is interpreted via EvalSub; a MakeTensorLit
       instruction is straightforward if it ever shows up in a profile.
   1d. [DONE v0.46.1] Recursive local functions. A recursive closure is genuinely
       cyclic and `captured` is a plain Arc<HashMap> that cannot contain itself, so
       the old code did a two-step dance (build the fn, insert it into a *second*
       copy of the map) that only reached one level deep — deeper recursion
       silently resolved through the flat call-site env, i.e. dynamic scoping.
       Replaced by FnSig::self_name: the callee binds its own name at call time, in
       both the VM (LoadCaptured checks it first) and the tree-walk path. Acyclic,
       depth-independent, and it deleted one of the two whole-env clones per
       definition. v0.46.2 extended it to MakeClosure, so a local `f(x) = …` that
       calls itself compiles instead of abandoning the enclosing body: 100k
       iterations of a body defining and calling a recursive local went
       2883 -> 1486 ms (1.94x). An anonymous lambda gets no self-name, since it
       has no name to recurse through.
   1e. [DONE v0.21.1] Loop instruction: bounded iteration (sum/prod/iterate/scan)
       compiled to a flat loop in the VM (Instruction::Loop(LoopForm, argc)) — the
       only recursion-analogue that is GPU-safe. The compiler pushes the operands
       (function + bounds/seed/count) and emits one Loop; run_vm drains them and
       calls the shared Val-based cores (agg_vals/iterate_vals/scan_vals), so
       results and errors are identical to tree-walk. These no longer force a
       fallback when used inside a compiled lambda body. (integral/deriv/map/filter/
       reduce still fall back — they need unevaluated args / bespoke handling.)
   1f. [DONE v0.21.1] Moved the Instruction enum (+ new LoopForm) to src/vm.rs; it
       depends only on crate::ast (Op, Expr), never on Val, so src/gpu/ can import
       it without pulling in eval.rs. run_vm/Compiler stay in eval.rs (they need Val).
   1k. [DONE v0.47.1] LoadCapturedSlot — a captured name is resolved to a constant-
       pool index at compile time instead of hashing the string on every access.
       Sound because `captured` never changes for the life of a Val::Fn.
       Worth 10-15%: a body doing 8 captured non-scalar reads per iteration went
       197 -> 177 ms per 100k (the read cost itself 113 -> 96 ms), forward
       reference 62 -> 55 ms, recursive local fn 428 -> 385 ms. Smaller than the
       ~140 ns/access figure suggested, because the Val clone's atomic refcount
       bump — which no scheme avoids — is most of it, not the hash.
       Three names are kept out of the pool. Each would yield a *wrong value*
       rather than an error, so each has its own tests (tests.sh pool.*):
         (a) FnSig::self_name. A previous binding of the same name may sit in
             `captured`, so the body must resolve it against the function being
             applied. This turned up a real pre-existing bug: the scalar-inlining
             path had the same problem and no guard, so after `f = 100` the body
             of `f(n) = … f(n-1) …` read `f` as the literal 100 and the recursive
             call became implicit multiplication — f(3) gave 201 instead of 3.
             The tree-walk path and every non-scalar case were always correct.
             Fixed by guarding inlining and pooling alike in `load_captured`.
         (b) A nested closure's free_vars. The inner body is compiled against a
             hint map holding placeholders, so MakeClosure carries the pool's
             *names* and resolves them against the closure's real captured map
             when the closure is built. Resolving at compile time would freeze
             the placeholder, and every closure from one site would share it.
             Carrying names rather than values is also what keeps src/vm.rs free
             of any dependency on Val, which src/gpu/ relies on.
         (c) Names absent from `captured`, which stay LoadCaptured(String) so
             forward references keep resolving live (see 1j).

   1g. LoadBuffer instruction: GPU-side tensor indexing for captured buffers inside
       GPU lambda bodies (v2 GPU feature, see CONSIDERATIONS.md §15)
   1h. [DONE v0.46.2] Path writes in compiled bodies. Two different problems:
       - The *value* axis (`T[i] = v`) genuinely cannot use EvalSub: an assignment
         mutates a binding, and copying it into a sub-frame detaches it from the
         slot the write has to land in. Instruction::StoreAssign moves the root out
         of its local slot, runs the shared tree-walk writer on it (so index rules
         and error text are identical by construction), and moves it back —
         refcount 1 throughout, which is what keeps repeated writes O(1). A root
         arriving as a param or from the captured scope is seeded into a local
         first, which is also exactly the "assignment rebinds in this scope"
         semantics. 100k iterations of a body with two writes plus real
         arithmetic: 394 -> 321 ms.
       - The *cell* axis (`set(c[i], v)`) needs nothing special: a cell is a
         reference, so interpreting just that call still writes through to the one
         cell every holder shares. 100k iterations: 2.2 s originally, 66 ms now.
         A dedicated CellStore would shave the frame construction; not yet worth it.

   1i. [DONE v0.46.1] Expr::Member in compiled bodies. `ns.member` fell into the
       compiler's catch-all, so every body calling vec.normalize(...) / bits.and(...)
       — the entire namespaced library style, 31 call sites in libraries/mag.math
       alone — tree-walked. Measured: 1994 ms vs 34 ms for the same loop with the
       member hoisted to a plain name first, a 59x penalty with an invisible
       workaround. Now Instruction::Member{field,who} (`who` carried from compile
       time so error text matches the tree-walk arm exactly), plus static
       resolution of `ns.f(x)` straight to CallBuiltin. Now 37 ms.

   1j. [DONE v0.46.1] Forward references no longer disable compilation. Expr::Var
       returned Err(()) for a name absent from the captured snapshot, and the
       OnceLock cached that failure permanently — so `f(x) = g(x)+1` written above
       `g` tree-walked forever, 2260 ms vs 68 ms for the same pair in the other
       order. A 33x difference decided by line order alone. Unknown names now emit
       LoadCaptured, which resolves live and errors cleanly if truly undefined.

2.6. [DONE v0.46.2] Narrow closure capture to free names. Defining a closure used
   to snapshot the whole visible environment. At the top level that is only an Arc
   bump, but it pins env.vars at refcount >= 2, so the *next* Env::define
   deep-clones the globals via Arc::make_mut — and so does every definition after
   it. Top-level definition was therefore O(n^2): 500 defs 147 ms, 1000 529,
   2000 2005, 4000 8119.
   Now `capture_for` collects the names the body and the *parameter defaults* can
   read (defaults are evaluated in the captured scope by fill_defaults, and their
   names never appear in the body — the one gap that would have broken this) and
   snapshots only those. Linear now, and 100-600x faster in absolute terms:
   500 4 ms, 1000 7, 2000 8, 4000 14, 8000 32.
   The walker is deliberately conservative — it subtracts nothing for inner
   binders, because over-collecting costs an Arc bump and is shadowed by the frame
   at run time, while under-collecting breaks the closure. Sound because mathlang
   has no string type and no dynamic name lookup, so the names a body can reach
   are exactly the ones it spells. That is a property of the language, not of the
   analysis.
   NOT the same as `cfv`/collect_free_vars, which answers "which of the enclosing
   frame's slots must a nested lambda be handed" and so ignores captured names on
   purpose. Both exist; do not merge them.
   Side effects: closure memory is O(free names) instead of O(env), and env.vars
   is no longer pinned, so the in-place fast path for `T[i] = v` at top level is
   reachable again.
